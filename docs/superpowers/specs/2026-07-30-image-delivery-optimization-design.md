# 商品图片详情级压缩与回填设计

## 背景

生产环境当前已落盘的商品图片大多是手机原图。已核验的 15 张有效商品图共约 65.87 MiB，平均约 4.39 MiB，最大约 7.44 MiB；其中多数为 `5712 x 4284`。现有图片处理器的目标仅为 20 MiB，因此这些图片不会继续缩放，小程序列表和详情页仍会下载数 MiB 的单张图片。

本次只处理商品图片（`PRODUCT_IMAGE`）：上传时不保存原图，只保存一份可同时用于列表、封面和详情的 JPEG 压缩图；生产已存在的有效商品图片通过独立运维命令一次性回填。

## 目标与边界

| 项目 | 确定规则 |
| --- | --- |
| 适用范围 | 仅 `PRODUCT_IMAGE`；不改变营业执照、头像及其他业务文件的处理规则 |
| 最终格式 | `image/jpeg`，对象键扩展名固定为 `.jpg` |
| 尺寸 | 等比缩小、不放大，最长边不超过 `1280px` |
| 体积目标 | 优先命中 `300 * 1024` bytes（下文称 300KB） |
| 硬上限 | 严格不超过 `500 * 1024` bytes（下文称 500KB） |
| 原图 | 仅在 HTTP 请求或处理临时文件中短暂存在；上传成功和回填完成后均不保留原始高清文件 |
| 存储变体 | 每个商品文件只保留一份 `detail-v1` JPEG，不生成额外封面或缩略图 |
| 存量处理 | 独立、可中断续跑的命令；绝不在 API 服务启动时自动回填 |

本次不引入 CDN、异步队列、水印、人工内容审核或客户端本地压缩。原始上传大小上限继续保持现有 40 MiB；超过该限制或无法压到 500KB 的文件都拒绝上传，不允许回退保存原始字节。

## 方案选择

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 保持原格式并仅降低质量 | 不采用 | PNG、HEIC 等格式很难稳定满足 500KB，且文件扩展名与实际内容的一致性更复杂 |
| 前端或小程序本地压缩 | 不采用 | 设备能力和实现不一致，无法约束管理端、API 和历史文件 |
| 服务端统一 JPEG + 版本化对象键 | 采用 | 体积和格式可控，保留同一个 `file_id`，同时利用新 URL 避免客户端继续使用旧缓存 |

## 图片处理契约

### 输入与输出

服务端继续接受 JPEG、PNG、WebP、HEIC、HEIF 声明类型，但只以实际文件字节的检测和 libvips 解码结果为准。文件名、表单 MIME 和扩展名都不能绕过内容校验。

`PRODUCT_IMAGE` 的处理固定执行以下步骤：

1. 解码并校验为允许的静态图片。
2. 应用 EXIF 方向（`autorot`），转为 sRGB，移除 EXIF 等元数据。
3. 对透明图片以白色背景合成。
4. 按最长边限制等比缩小至不大于 1280px，绝不放大。
5. 使用 JPEG 输出并校验输出魔数、MIME、尺寸和字节数。

输出 profile 固定为 `detail-v1`，其候选尺寸为 `1280`、`1120`、`960`，候选 JPEG 质量从高到低为 `82`、`78`、`74`、`70`、`66`。处理器以确定性顺序生成候选：

1. 只要存在不超过 300KB 的候选，选择画面尺寸最大、质量最高的那个。
2. 如果无法达到 300KB，则选择仍不超过 500KB 的画面尺寸最大、质量最高的候选。
3. 如果所有候选都超过 500KB，处理失败；不写入原图、不将文件标为 `PASS`。

这使 300KB 成为质量与流量的优先目标，同时保证任何成功响应的最终产物都绝不超过 500KB。

### 错误语义

| 情况 | 结果 |
| --- | --- |
| 伪装文件、损坏图片、无法解码、输出不是 JPEG | 返回现有非法上传错误；文件记录保持 `PENDING` |
| vips 缺失、超时、临时文件 I/O 失败 | 返回内部处理错误；文件记录保持 `PENDING`，可重试 |
| 无候选满足 500KB | 返回非法上传错误；不保存任何原始或超限字节 |
| 数据库更新失败 | 删除刚写入的新对象，保留 `PENDING` 记录；不得返回成功 |

`confirm` 不再能够把未成功处理的 `PENDING` 文件提升为 `PASS`。只有上传处理完整落盘、数据库元数据已更新的文件可以确认，确认接口仅保持幂等性。

## 上传与访问链路

### 新上传

`POST /files/presign` 在 `biz_type=PRODUCT_IMAGE` 时直接生成版本化键，例如 `product_image/detail-v1/F<业务流水号>.jpg`。预登记的最终 MIME 是 `image/jpeg`，请求声明的源 MIME 只用于允许类型的前置校验。

`POST /files/upload` 将原始请求体读入受大小限制的临时处理范围，调用 `detail-v1` 处理器，再以原子写入方式落盘：先写同目录临时文件并关闭、校验，再 `rename` 成最终对象。成功后以一个数据库更新同步 `object_key`、`url`、`mime_type=image/jpeg`、`size_bytes` 和 `scan_status=PASS`。任何处理或校验失败都不留下可访问对象。

`FileRecord.ID` 保持不变，因此 `product_images.file_id`、`products.cover_file_id`、收藏、浏览历史和意向记录都不需要迁移。API 返回的图片 URL 仍由同一文件记录计算。

### 缓存与小程序加载

`product_image/detail-v1/` 是不可变对象键前缀。静态图片响应对该前缀设置 `Cache-Control: public, max-age=31536000, immutable`；其他业务文件保留现有响应策略。以后变更图片内容必须创建新的版本化键，不能覆盖已有版本化对象，这样小程序、浏览器和反向代理不会继续命中旧图缓存。

小程序商品卡片、首页商品流和分类列表的 `Image` 组件启用 `lazyLoad`。详情首图保持立即加载，非首屏图片延迟加载。列表和详情仍使用同一份详情级 JPEG，不新增缩略图存储。

## 生产存量回填

### 候选和排除规则

新增 `backend/scripts/backfill_product_images` 一次性命令，不通过 HTTP 上传接口，也不创建 API Server。它仅处理同时满足下列条件的 `file_records`：

1. `biz_type = PRODUCT_IMAGE` 且 `scan_status = PASS`；
2. 文件被 `product_images.file_id` 或 `products.cover_file_id` 引用；
3. 实际对象存在且可读；
4. 按 `file_records.id` 去重。

营业执照、未引用的孤儿文件、`PENDING` 文件、缺物理文件和悬空封面不作猜测性修复。命令会把这些情况写入异常清单，供单独处置。已核验的生产数据中，预计有 11 条有效候选；该数量只是运行前基线，实际执行以前必须重新 dry-run 复核。

### 可恢复状态

新增显式迁移，创建 `image_backfill_runs` 与 `image_backfill_items` 账本表，迁移使用 `CREATE TABLE IF NOT EXISTS`，并由现有显式迁移命令执行。账本至少记录：运行 ID、文件 ID、源/目标对象键、profile 版本、源/输出 SHA-256、源/输出大小、处理状态、尝试次数、租约到期时间和错误码。

单项状态机为：

`PENDING -> PROCESSING -> STAGED -> COMMITTED | SKIPPED | FAILED`

命令参数固定为：

| 参数 | 行为 |
| --- | --- |
| `--dry-run` | 默认模式；仅扫描、解码、估算输出体积和生成清单，不写对象或数据库 |
| `--apply` | 显式允许执行写入 |
| `--run-id` | 绑定或继续一个账本运行；重复执行会接管已过期租约并跳过已提交项 |
| `--after-id`、`--limit` | 支持分段执行和 canary |
| `--workers` | 默认 1；生产回填保持单并发，避免和正常商品图片变更竞争 |

单项的写入顺序如下：

1. 读取旧对象并计算源哈希，在临时文件生成和验证 `detail-v1` JPEG。
2. 写入新的版本化对象键，完成 fsync 和输出哈希校验，账本标记为 `STAGED`。
3. 短事务条件更新同一条 `file_records` 的对象键、URL、MIME 和最终大小，并将账本标为 `COMMITTED`。
4. 数据库提交后删除旧对象；删除失败记录为待清理，后续使用同一运行 ID 重试，不影响新 URL 可用性。

数据库提交前若失败，旧对象和旧文件记录都保持可用，新临时对象会删除。数据库提交后会暂存旧对象直到删除成功；这只是失败恢复窗口，不是保留原图的长期策略。每次重跑按账本哈希确认已经完成的动作，不能重复压缩同一张已经提交的 `detail-v1` 图片。

执行期间必须安排维护窗口，至少阻止文件上传、商品图片编辑和商品删除。现有商品删除逻辑可能在事务外删除物理对象，不能与回填并发运行。

## 配置、部署与发布顺序

生产容器已安装 `vips 8.14.1`，实际上传卷挂载为宿主机 `/home/yu/services/secondhand-market/runtime/uploads` 到容器 `/data/uploads`，Web 的 `/uploads/` 已反向代理给 API。回填命令必须通过同一镜像、同一容器网络和同一上传卷执行，不能在宿主机硬编码不存在的 `/data/uploads` 路径。

新运行时配置新增详情图相关项，并在启动时校验：最大边为正数、质量阶梯合法、`0 < target <= hard <= FILE_UPLOAD_MAX_MB * 1024 * 1024`，生产环境图片处理驱动必须为 vips；未知驱动或 passthrough 直接拒绝启动。

上线前必须显式调整当前生产环境：

| 配置 | 发布值 |
| --- | --- |
| `AUTO_MIGRATE` | `false` |
| `SEED_DEFAULTS` | `false` |
| `FILE_PUBLIC_BASE_URL` | 空值，由 API 的相对 `/uploads/...` 路径提供访问 |

发布步骤：

1. 发布并验证可解析相对 `/uploads/...` 的小程序版本。
2. 构建包含 API、显式迁移命令、回填命令和 migrations 的镜像，但不自动运行回填。
3. 显式执行账本迁移，核验表结构；再发布后端并验证新上传 JPEG、小程序展示和响应缓存头。
4. 开启维护窗口，先以 `--dry-run` 复核候选和异常清单，再以 `--apply --limit 1` 做单张 canary。
5. 验证 canary 的详情、封面和列表 URL，确认不超过 500KB 后分批完成其余候选。
6. 核对账本没有未处理清理项，保留异常清单并关闭维护窗口。

## 测试与验收

| 层级 | 必测内容 |
| --- | --- |
| media 单元测试 | JPEG 输出、最长边不超过 1280、EXIF 旋转、透明 PNG 白底、去元数据、300KB 优先选择、500KB 硬拒绝、vips 失败不回退原图 |
| 上传集成测试 | `PRODUCT_IMAGE` 预签名返回 `.jpg` 版本化键；成功后实际字节、MIME、对象键、URL、数据库大小一致；失败时无可访问文件且状态不为 `PASS`；confirm 不能提升 `PENDING` |
| 回填测试 | dry-run 无写入、共享文件 ID 仅处理一次、已提交项可跳过、源损坏或数据库/删除失败不丢旧图、恢复运行会完成待清理项 |
| 小程序测试 | 列表卡片图片启用 `lazyLoad`，详情首图与延迟图片行为符合约定 |
| 端到端验收 | 新上传和回填后商品封面、列表、收藏、浏览历史和详情均能展示同一 JPEG；每个成功商品图片都不超过 500KB |

## 明确验收标准

1. 任意成功上传的 `PRODUCT_IMAGE` 都是最长边不超过 1280px 的 JPEG，且文件大小不超过 500KB。
2. 对可压至 300KB 的源图，系统优先保存满足该目标的最高保真候选。
3. 无法满足 500KB 的图片上传失败，绝不保存或返回原始高清图。
4. 每个商品图片只存一份 `detail-v1` JPEG；不会产生封面或缩略图副本。
5. 有效历史商品图片可以 dry-run、canary、分段执行和中断续跑，且不会改变关联的 `file_id`。
6. 回填完成后旧高清对象被删除；无法删除的对象有可追踪的账本项，直到后续清理成功。
7. 小程序列表不再并发加载不可见商品图，版本化图片 URL 可长期缓存。
