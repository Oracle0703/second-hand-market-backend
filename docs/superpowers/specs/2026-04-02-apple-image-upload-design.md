# 苹果图片上传与统一压缩设计

## 背景

当前后端上传链路支持 `presign -> upload -> confirm`，但图片处理能力较弱：

1. 前端文件选择已放开 `image/heic`、`image/heif`，后端仍主要按白名单和简单 MIME 探测处理。
2. 上传接口当前单文件限制为 `5MB`，苹果设备原图较容易超过该阈值。
3. 服务端上传后直接落盘，没有统一压缩，导致图片体积大、带宽与存储成本偏高。

本次需求是支持苹果常见图片格式上传，并对所有图片统一压缩后存储。

## 目标

1. 支持普通图片与苹果常见图片格式上传：`jpg/jpeg/png/webp/heic/heif`。
2. 苹果 `Live Photo` 仅处理其中静态图片文件，不处理配套 `mov` 视频。
3. 所有上传图片统一进入压缩流程。
4. 压缩后优先尽量控制在 `1MB` 内。
5. 如果压到质量/尺寸下限后仍超过 `1MB`，只要最终文件不超过 `10MB`，仍允许上传。
6. 尽量保留原格式输出，不强制统一转码为 `jpeg/webp`。

## 非目标

1. 不支持 `Live Photo` 配套视频上传、存储、播放。
2. 不在本次实现中引入 CDN、水印、异步转码队列。
3. 不在前端增加本地压缩逻辑，压缩统一由后端处理。
4. 不对图片做内容审核或病毒扫描增强。

## 用户场景

### 场景 1：商家注册上传营业执照

商家从苹果手机导出或直接选择营业执照图片，图片可能为 `heic/heif` 或较大尺寸的 `jpeg`。后端应接受上传、压缩并存储，注册流程不因图片格式或体积过大而频繁失败。

### 场景 2：商家上传商品图

商家上传商品图片时，无论是苹果图片还是普通图片，后端都应在保存前执行统一压缩，减小图片体积，同时尽量保留原始格式。

## 方案选型

### 方案 A：后端内新增图片处理服务，Docker 安装原生依赖

通过 Linux Docker 安装 `libvips` 及 `libheif` 相关依赖，Go 服务在上传链路中调用图片处理模块，完成格式识别、压缩、缩放和编码。

优点：

1. 能覆盖 `heic/heif` 读取与输出。
2. 性能和内存占用更适合服务端批量图片处理。
3. 处理逻辑可以集中在后端，前端无需分平台适配。

缺点：

1. Docker 镜像需要补充系统依赖。
2. 本地开发环境如果不使用容器，需要额外说明依赖要求。

### 方案 B：只用纯 Go 图像库处理

优点：

1. 依赖简单，构建链更纯。

缺点：

1. 对 `heic/heif` 支持不足。
2. 很难满足“尽量保留苹果原格式”的要求。

结论：采用方案 A。

## 总体设计

### 上传链路调整

上传主流程保持不变，仍为：

1. `POST /api/v1/files/presign`
2. `POST /api/v1/files/upload`
3. `POST /api/v1/files/confirm`

其中压缩逻辑放在 `files/upload` 阶段，流程改为：

1. 校验 `file_id`、`object_key`、上传身份和业务类型。
2. 读取上传文件的真实 MIME 与图片元信息。
3. 若不是允许的图片格式，则拒绝上传。
4. 调用图片处理模块执行统一压缩。
5. 将压缩后的结果写入本地存储。
6. 将数据库中的 `mime_type`、`size_bytes` 更新为压缩后的最终结果。

### 支持格式

允许的静态图片格式：

1. `image/jpeg`
2. `image/png`
3. `image/webp`
4. `image/heic`
5. `image/heif`

显式不支持：

1. `image/gif`
2. `video/quicktime`
3. `video/mov`
4. 其他视频、文档与二进制格式

### 大小规则

区分“原始上传限制”和“最终存储限制”：

| 规则 | 数值 | 说明 |
| --- | --- | --- |
| 原始上传上限 | `10MB` | 允许苹果原图先进入压缩流程 |
| 目标压缩体积 | `1MB` | 优先追求的输出目标 |
| 最终允许上限 | `10MB` | 达到质量/尺寸下限后仍大于 `1MB` 时的兜底阈值 |

判定逻辑：

1. 原始文件大于 `10MB`，直接拒绝上传。
2. 压缩后若 `<=1MB`，直接保存。
3. 压缩后若 `>1MB`，继续尝试降质量与缩尺寸。
4. 到达质量/尺寸下限后，若结果 `<=10MB`，仍允许上传。
5. 到达下限后若结果仍 `>10MB`，拒绝上传。

## 图片处理策略

### 格式识别

服务端应使用更稳定的内容识别方式，而不是只依赖 `http.DetectContentType` 的 512 字节探测结果。

识别结果用于：

1. 判断是否为允许格式。
2. 选择对应解码器与编码器。
3. 计算输出扩展名和最终 `mime_type`。

### 压缩原则

1. 所有图片统一压缩。
2. 尽量保留原格式输出。
3. 先降质量，再降尺寸。
4. 设定质量下限与尺寸下限，避免图片被压得不可用。

### 具体处理顺序

1. 读取原图并识别真实格式。
2. 如果格式非法，返回上传文件不合法。
3. 若原图已足够小，也仍走一次规范化输出，确保链路一致。
4. 先按原格式执行质量压缩。
5. 如果结果仍大于 `1MB`，则按比例逐步缩小尺寸。
6. 每次压缩后检查输出体积。
7. 到达预设下限后，如果仍大于 `1MB`，只要不超过 `10MB` 也允许保存。

### 各格式处理策略

| 原格式 | 输出格式 | 处理策略 |
| --- | --- | --- |
| `jpeg/jpg` | `jpeg` | 质量压缩优先，必要时缩尺寸 |
| `png` | `png` | 保留 `png`，优先做压缩与尺寸缩放 |
| `webp` | `webp` | 保留 `webp`，按质量压缩 |
| `heic/heif` | `heic/heif` | 保留苹果格式，依赖系统库完成解码与编码 |

说明：

1. `png` 如果是证照、白底材料，保留 `png` 可避免无谓格式变化。
2. `heic/heif` 保持原格式是本次需求的重要约束，因此依赖容器内系统库支持。

## 后端模块拆分

建议新增独立图片处理模块，例如：

1. `backend/internal/media` 或 `backend/internal/images`
2. 由上传 handler 调用，不把复杂处理逻辑堆在 `file_handlers.go`

职责拆分如下：

| 模块 | 职责 |
| --- | --- |
| `file_handlers` | 接收请求、鉴权、调用图片处理服务、更新文件记录 |
| 图片处理服务 | 识别图片格式、压缩、缩放、输出结果 |
| 格式映射工具 | MIME 与扩展名互转、输出格式映射 |
| 上传存储逻辑 | 将处理后的字节写入本地文件系统 |

## 接口与数据影响

### `POST /files/presign`

变更点：

1. 最大允许 `file_size` 从当前 `5MB` 提升到 `10MB`。
2. 继续允许 `jpeg/png/webp/heic/heif`。
3. 生成的 `object_key` 扩展名仍优先基于请求 MIME 或文件名后缀。

### `POST /files/upload`

变更点：

1. 不再简单按原文件直接落盘。
2. 改为压缩后再写文件。
3. 最终入库的 `mime_type` 与 `size_bytes` 以压缩结果为准。
4. 如果输出格式与原始文件扩展名不一致，需要同步修正最终文件扩展名和 `object_key`；若实现保持原格式，则通常无需改动 `object_key` 规则。

### `POST /files/confirm`

无需业务协议变更，但它看到的是压缩后已经落盘的最终文件。

### 数据库

不需要新增表字段，复用 `files` 表既有字段：

| 字段 | 用途 |
| --- | --- |
| `mime_type` | 记录压缩后的最终 MIME |
| `size_bytes` | 记录压缩后的最终体积 |
| `object_key` | 文件存储路径 |
| `url` | 文件访问地址 |

## Docker 依赖

部署环境为 Linux Docker，需要在镜像中安装图片处理依赖，以支持 `heic/heif`。

依赖目标：

1. 支持 `heic/heif` 解码与编码。
2. 支持 `jpeg/png/webp` 压缩与缩放。

镜像层面需要补充：

1. `libvips`
2. `libheif`
3. 对应开发头文件或运行时依赖

具体包名可根据基础镜像选择：

1. Debian/Ubuntu 系：`libvips`, `libheif`, `libde265`, `libaom` 等相关包
2. Alpine 系：选择可用的 `vips`、`heif` 对应包

实现阶段需要同步更新 Dockerfile 与部署说明。

## 错误处理

### 返回现有错误码

继续复用当前上传非法错误码 `10008`，用于：

1. MIME 非法
2. 真实内容不是受支持图片
3. 原始文件大于 `10MB`
4. 压缩失败
5. 压缩后仍大于 `10MB`

### 日志

建议在服务端记录以下信息，便于排查：

1. 请求声明 MIME
2. 服务端识别 MIME
3. 原始大小
4. 压缩后大小
5. 输出格式
6. 是否触发尺寸缩放

## 前端影响

前端当前商品页与注册页已经放开 `heic/heif` 选择，主要调整为：

1. 上传提示文案与帮助说明更新，明确支持苹果图片格式。
2. 如有图片大小提示，需同步从 `5MB` 更新为 `10MB`。

前端无需新增压缩逻辑。

## 测试设计

### 单元测试

覆盖点：

1. 允许 MIME 白名单扩展与判定。
2. MIME 与扩展名映射。
3. 压缩策略分支：直接达标、降质量达标、缩尺寸达标、到达下限后仍允许、超过 `10MB` 拒绝。

### 集成测试

至少覆盖以下场景：

| 场景 | 预期 |
| --- | --- |
| 上传 `jpeg` 成功 | 返回成功并可访问 |
| 上传 `png` 成功 | 返回成功并可访问 |
| 上传 `webp` 成功 | 返回成功并可访问 |
| 上传 `heic` 成功 | 返回成功并可访问 |
| 上传 `heif` 成功 | 返回成功并可访问 |

### 回归点

1. 商家注册上传营业执照可用。
2. 商品创建上传商品图可用。
3. 商品编辑继续追加图片可用。
4. 本地存储 `/uploads/...` 访问正常。

## 风险与应对

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| `heic/heif` 编码支持不足 | 取决于镜像内系统库能力 | 在 Docker 中固定依赖版本并增加启动前验证 |
| 压缩耗时上升 | 上传时增加 CPU 开销 | 控制图片上限为 `10MB`，避免极端大文件 |
| `png` 保留格式后体积下降有限 | 无损格式压缩空间有限 | 允许最终在 `1MB~10MB` 范围内保存 |
| MIME 识别与文件后缀不一致 | 可能出现声明类型与真实类型不同 | 始终以真实识别结果为准 |

## 验收标准

1. 商家可上传 `heic/heif` 图片完成注册与商品发布。
2. 所有受支持图片都经过后端统一压缩后再存储。
3. 压缩优先目标为 `1MB`，但允许在质量/尺寸下限后保留 `<=10MB` 的结果。
4. `Live Photo` 对应的图片文件可上传，配套视频文件会被拒绝。
5. 原始文件超过 `10MB` 会被拒绝。
6. 上传成功后数据库记录的是压缩后的最终 `mime_type` 和 `size_bytes`。
