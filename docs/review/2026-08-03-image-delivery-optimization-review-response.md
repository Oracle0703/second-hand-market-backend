## 二、采纳或修正后采纳的意见

| ID | 审核意见 | 判定 | 处理决定 |
| --- | --- | --- | --- |
| A-1 | dry-run 与规格不一致 | 采纳 | dry-run 必须真实解码并执行候选压缩，输出预计尺寸、命中档位和失败原因；只禁止写最终对象、业务表和账本。`Processed` 改为“已评估数量”，避免把只枚举候选误称为演练。规格 L106 已明确“解码、估算输出体积”。 |
| A-2 | `MaxEdge` 可配置但候选网格固定；500KB 硬上限又可被环境变量突破 | 采纳 | `detail-v1` 是版本化且不可变的输出契约，1280px、300KB、500KB 和质量阶梯改为代码常量，不再允许环境变量改变同一 profile 的语义。未来调整必须发布 `detail-v2`。 |
| A-3 | 最多生成 15 个候选且缺少显式超时 | 采纳 | 按边长降序、质量降序处理；记录首个不超过 500KB 的兜底，命中首个不超过 300KB 的候选立即返回。保留现有从 HTTP request context 到 `exec.CommandContext` 的取消链路，并在其外增加明确处理超时；现有 vips 处理器已经使用“首个达标即返回”的模式。 |
| A-4 | 提交后立即删除旧对象可能导致旧 URL 短暂裂图 | 采纳 | 数据库切换后旧对象进入延迟清理，默认至少保留 24 小时；账本记录 `cleanup_after`、`cleanup_status`。清理命令到期后再删除，且汇总必须包含待清理、清理完成和清理失败数量。 |
| A-5 | 不同 run 或两个 apply 可并发，缺少程序化互斥 | 修正后采纳 | 增加命令级全局 apply 锁，生产同时只能存在一个回填执行实例；删除 `--workers`，内部固定单并发。仅依靠人工 run-id 纪律不够，但也不采用 `file_id` 全局唯一，原因见“不采纳项”。 |
| A-6 | `LeaseUntil`、`Attempts`、`SKIPPED` 与状态机脱节 | 采纳 | 单并发模型下删除租约与 `SKIPPED` 账本状态；未进入候选的数据只写 JSON 异常清单。保留 `Attempts` 和 `ErrorCode`，并明确 `FAILED` 只在相同 run 使用显式 `--retry-failed` 时重试和递增次数。 |
| A-7 | `PassthroughProcessor` 无法兑现完整 detail profile | 修正后采纳 | 不要求 passthrough 复刻 vips 候选阶梯，但要写清最小契约：仅接受实际字节为 JPEG/PNG 的小图，统一重编码为 JPEG；不做缩放，超过 1280px 或 500KB 就失败。生产仍强制 vips；完整 profile 测试使用 fake processor 和真实 vips 集成测试。 |
| A-8 | 商家图片归属按 `actor.UserID` 校验会阻断同商户 STAFF 账号 | 采纳 | 商品关联校验必须按 `MerchantID` 归属，而不是要求上传账号 ID 与编辑账号 ID 相同。可通过上传账号关联 `merchant_accounts.merchant_id` 校验，或为文件记录补充商户归属字段。 |
| A-9 | 对象键存在“双 F”和上传/回填口径歧义 | 采纳 | 明确为：新上传 `product_image/detail-v1/{BuildBizNo("F")}.jpg`；回填 `product_image/detail-v1/F{file_id}.jpg`。两者用途不同，但都必须保证目标键稳定且不覆盖既有版本化对象。 |
| A-10 | 详情 Swiper 仅写 `lazyLoad={idx > 0}` 不能证明真实按需加载 | 修正后采纳 | 本项目使用的 Taro 3.6.34 类型注释明确说 `lazyLoad` 只针对 `page/scroll-view` 下的图片；微信当前在线文档只描述“进入上下三屏时加载”，两者口径不完全一致。为保证微信/抖音两端确定性，列表、首页和分类继续使用 `lazyLoad`；详情轮播改为受控 `current`，只为当前项及相邻项设置真实 `src`。测试验证状态切换后的 `src` 集合，不再只做源码正则断言。 |
| A-11 | Cache-Control 测试位置、回填汇总和 HEIC 镜像验证不足 | 采纳 | Cache-Control 在 `GET /uploads/...` 测试中断言；回填汇总增加清理计数；生产镜像增加 JPEG/PNG/WebP/HEIC 到 JPEG 的 vips 冒烟，并继续检查运维二进制和迁移文件存在。 |
| A-12 | `FAILED` 重试和旧图清理协议未说明 | 采纳 | 计划补齐显式失败重试规则和延迟清理协议。迁移 down 文件不作为缺陷处理，原因见 N-11。 |
| A-13 | `confirm` 不能把 `PENDING` 提升为 `PASS` 是现有行为 | 保留为验收 | 不把它描述为新实现能力，但保留回归测试。该检查是上传安全边界，已有实现不代表可以移除测试。 |

## 三、不采纳或仅记录为后续演进的建议

| ID | 建议 | 判定 | 不采纳理由与证据 |
| --- | --- | --- | --- |
| N-1 | 本次新增 `list-v1`/缩略图 | 不采纳，记录后续 | 已确认规格明确“每个商品文件只保留一份 `detail-v1`，不生成额外封面或缩略图”（规格 L19、L161）。从平均约 4.39MiB 降至约 300KB 已解决本期主要流量问题；新增多变体会扩大数据模型、回填和清理范围。审核材料本身也承认单图方案可作为 MVP。 |
| N-2 | 改为 500KB 内一律优先保真，不再优先 300KB | 不采纳 | 300KB 是已确认的产品目标和明确验收标准（规格 L16、L48-L52、L159），审核只给出假设候选，没有真实图片的可读性对比或用户反馈证明当前阈值不可接受。可在实现验收时加入样本目视检查，但不在本轮改变目标。 |
| N-3 | 为账本增加 `file_id` 全局唯一 | 不采纳，采用替代方案 | 账本包含 `profile_version`，未来 `detail-v2` 需要允许同一 `file_id` 再迁移；全局唯一会永久阻断这一合法路径。采用“排除当前 profile + 全局 apply 锁 + `source_key != target_key` 删除防御”可解决本次风险而不牺牲版本演进。 |
| N-4 | 必须增加覆盖所有写接口的应用级 maintenance flag | 修正后采纳运维目标，不采纳指定实现 | 规格已经要求冻结上传、图片编辑和商品删除（规格 L121），当前生产候选基线约 11 条（L92）。对一次性小规模迁移增加跨模块全局维护状态会扩大 API 行为面；采用发布开关、明确写冻结、全局回填锁和发布前检查即可。若实际候选量显著增长，再升级为应用级维护模式。 |
| N-5 | 删除 Dockerfile 字符串合约测试，只保留镜像构建 | 不采纳 | 源码合约测试能快速、确定地发现运维二进制或 migrations 未复制，镜像构建则验证真实产物，两者覆盖不同失败面。保留静态合约测试，但将断言集中在必要产物，不绑定无关空白或完整 `COPY` 行格式。 |
| N-6 | 直接比较 SQLite AutoMigrate 与 MySQL 手写 SQL 的 DDL 等价性 | 不采纳指定实现，采纳风险 | `MigrateSchema` 走 GORM/SQLite 测试路径，而显式迁移命令明确拒绝非 MySQL 驱动；两种数据库的类型、默认值和索引 DDL 不能做可靠文本等价比较。改为共享行为契约测试：分别验证必需列、唯一约束和状态长度；MySQL 集成环境执行真实 `0004` 后跑同一组断言。 |
| N-7 | 允许 admin 上传的 `PRODUCT_IMAGE` 直接关联商家商品 | 不采纳 | 当前管理端没有 admin 商品创建/编辑入口，商品路由属于 merchant 权限组；通用上传接口允许 admin 上传并不等于存在 admin 代商家关联图片的业务流程。贸然放开会缺少目标 `merchant_id`，反而破坏归属校验。 |
| N-8 | 已达到尺寸/体积的旧图全部跳过重编码 | 不采纳 | 旧图即使体积合规，也不一定是 JPEG、sRGB、已旋转、白底或已去元数据，更没有 `detail-v1` 版本化键。只按尺寸和体积跳过无法证明满足 profile；仅跳过已经位于 `detail-v1` 前缀且元数据一致的文件。 |
| N-9 | 商家编辑页预览必须展示服务端最终 JPEG | 不采纳 | 当前 `createObjectURL` 是上传前本地预览，不是最终产物验收。上传成功后的详情和重新进入编辑页仍读取服务端 URL；为预览再做一次上传或本地复刻 vips 会增加流量或产生跨端差异。界面文案不承诺预览与压缩结果逐像素一致即可。 |
| N-10 | 将 Swiper 内 `lazyLoad` 的无效性描述为所有目标平台已实测事实 | 修正表述，不否定处理建议 | `miniapp/node_modules/@tarojs/components/types/Image.d.ts:24-28` 支持审核对微信/Taro 的担忧，但微信当前在线文档没有相同限定，抖音端也未在本仓库做运行时验证。因此文档应写成“不能保证按需请求”，不写成两端都已证实“一定无效”。A-10 的受控 `src` 方案仍采纳。微信文档：<https://developers.weixin.qq.com/miniprogram/dev/component/image.html>。 |

## 六、最终回复

两份审核都识别到了真实风险，尤其是回填重入、崩溃恢复和发布过渡三项。MIME 意见指出了需要澄清的实现边界，但其“必现 P0”定性被计划 L145 反证。综合判断不是“全部照单全收”，而是：接受经代码核验的问题事实，选择符合当前代码边界且不会阻断未来 profile 版本演进的修法。

当前实施计划状态为：**需要修订，不可直接开工**。原计划修订后应再次做一次聚焦 P0 数据安全路径的文档审核，再进入 TDD 实现。
