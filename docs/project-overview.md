# 项目总体说明（project-overview）

## 默认假设（需求缺失补全）
1. 本期只建设“商家后台管理系统”，不包含买家端、小程序端、客服端。
2. 商家仅支持企业主体注册；商家在 `PENDING/REJECTED` 可登录但仅获得受限制权限（restricted login），审核通过后获得完整商家权限。
3. 本期角色启用：`PlatformAdmin`（平台管理员）、`MerchantOwner`（商家主账号）；`MerchantStaff`（子账号）仅预留。
4. 商品发布后不做平台逐条审核，平台审核对象是商家资质。
5. “成交/关闭”采用轻量订单流，不接入支付、退款、售后。
6. 订单会锁定商品，创建订单后商品进入 `LOCKED`，同一商品仅允许 1 个未完成订单。
7. 前端采用单 React 应用响应式适配 PC 与移动端，不拆双工程。
8. 后端默认技术栈为 Gin + GORM；数据库使用 MySQL 8.x，缓存与会话辅助使用 Redis。
9. 图片上传采用对象存储抽象（开发环境可 MinIO，生产可 OSS/S3），后端只负责上传凭证与元数据落库。
10. 分类采用“商户自有两级分类”，商家可在后台维护自己的一级/二级分类。

## 1. 项目背景与目标
“二手交易项目商家后台管理系统”用于支撑商家完成准入与商品经营流程。系统核心目标：

1. 建立合规准入链路：商家注册、平台审核、审核结果追踪。
2. 建立经营闭环：商品发布、编辑、上架、下架、锁定、成交、关闭。
3. 建立运营可控性：平台可查看商家与商品状态、审计关键操作。
4. 建立可持续演进基础：预留商家子账号与更复杂订单能力。

## 2. 本期范围与非范围

### 2.1 本期范围（In Scope）
1. 认证与账户：注册、登录、刷新令牌、退出登录。
2. 商家审核：管理员审核列表、审核详情、审核通过/驳回。
3. 商品管理：新增、编辑、详情、列表、上下架、关闭。
4. 轻量订单：创建、完成、关闭；与商品状态联动。
5. 分类管理：商家自主管理本商户一级/二级分类，并用于商品分类选择。
6. 文件上传：商品图片、资质图片上传与管理。
7. 平台审计：关键业务动作记录（谁、何时、做了什么、结果如何）。
8. 基础非功能能力：鉴权、错误码、分页筛选、日志追踪、移动端适配。

### 2.2 非范围（Out of Scope）
1. 买家侧浏览、下单、支付与履约。
2. 支付、退款、发票、售后争议处理。
3. 营销体系（优惠券、活动、推荐位竞价）。
4. 多语言、多租户、复杂审批流引擎。
5. 管理员管理管理员页面、平台级分类模板管理页面。

## 3. 角色与权限

| 角色 | 说明 | 关键权限 | 明确限制 |
| --- | --- | --- | --- |
| PlatformAdmin（SUPER_ADMIN） | 超级管理员 | 商家审核、查看全量数据、冻结商家、查看日志、初始化普通管理员 | 不编辑商家商品 |
| PlatformAdmin（ADMIN） | 普通管理员 | 商家审核、查看全量数据、查看日志 | 不可创建管理员，不编辑商家商品 |
| MerchantOwner | 商家主账号 | 注册/登录；`APPROVED` 后可管理本商家商品、创建/完成/关闭订单、查看本商家日志 | `PENDING/REJECTED` 仅允许入驻流程接口；不可访问其他商家数据、不可执行审核 |
| MerchantStaff（预留） | 商家子账号（未来） | 预留：按权限管理商品或订单 | 本期不开放创建与登录 |

## 4. 管理员账号来源与初始化策略
1. 本期管理员账号通过初始化脚本预置（例如 `backend/scripts/bootstrap_admin`），不提供后台创建管理员功能。
2. 本期区分 `SUPER_ADMIN` 与 `ADMIN` 两个管理员级别，权限由后端权限表或角色常量控制。
3. 管理员与商家共用登录页面，但登录请求中需带 `login_type=ADMIN/MERCHANT`，后端按账号域鉴权并返回角色权限。
4. 若未来需要“管理员管理管理员”，作为后续版本独立需求，不纳入本期范围。

## 5. 关键业务流程

### 5.1 注册 -> 审核 -> 登录
1. 商家提交注册资料（主体信息、联系人、营业执照等）。
2. 系统生成 `PENDING` 审核状态；账号可登录但只返回 `onboarding scope`。
3. `onboarding scope` 仅可访问入驻流程接口（`merchant/profile`、`merchant/reapply`、入驻资质上传）。
4. 管理员审核通过：状态变更为 `APPROVED`，后续登录返回完整商家权限（`full scope`）。
5. 管理员驳回：状态变更为 `REJECTED`，商家可继续用 `onboarding scope` 修改资料并重新提交。

### 5.2 发布商品 -> 上下架 -> 成交/关闭
1. 审核通过商家创建商品，初始状态 `DRAFT`。
2. 商家补全信息后上架，状态变更为 `ON_SHELF`。
3. 商家创建订单后，商品立即变更为 `LOCKED`（占用中）。
4. 订单完成：订单 `COMPLETED`，商品变更为 `SOLD`。
5. 订单关闭：订单 `CLOSED`，商品统一变更为 `OFF_SHELF`（避免自动继续售卖）。
6. 未锁定商品可手动关闭，状态变更为 `CLOSED`。

## 6. 商品状态与审核状态闭环

### 6.1 商家审核状态
`PENDING -> APPROVED | REJECTED`  
`REJECTED -> PENDING`（商家修改后重新提交）

### 6.2 商品状态
`DRAFT -> ON_SHELF`  
`ON_SHELF -> OFF_SHELF | LOCKED | CLOSED`  
`OFF_SHELF -> ON_SHELF | CLOSED`  
`LOCKED -> SOLD | OFF_SHELF`（由订单完成/关闭驱动）  
`SOLD`、`CLOSED` 为终态（本期不可逆）

### 6.3 订单状态（轻量）
`CREATED -> COMPLETED | CLOSED`

## 7. 技术架构与选型

### 7.1 前端
1. React + TypeScript + Vite。
2. 路由：React Router（按角色访问控制）。
3. 状态管理：推荐 TanStack Query + 轻量全局状态（如 Zustand）。
4. UI：响应式布局，PC 表格视图 + 移动端卡片视图。

### 7.2 后端
1. Go + Gin：路由清晰、生态成熟、性能与开发效率平衡。
2. GORM：降低 CRUD 与关联开发成本，适合业务快速迭代；复杂查询可用 Raw SQL 补充。
3. MySQL：事务与关系建模能力稳定，适合后台管理业务。
4. Redis：登录会话、刷新令牌黑名单、限流计数。

### 7.3 为什么不在本期替换为更重方案
本期重点是业务闭环与稳定上线，不是极致性能优化。Gin + GORM 组合足以支撑初期体量；后续如出现复杂读写压力，可按模块引入 `sqlc`/读写分离/缓存分层，而无需推翻现有接口契约。

## 8. 仓库定位说明
1. 当前仓库采用“前后端 + 文档”单仓组织方式，目录包含 `frontend/`、`backend/`、`docs/`。
2. 仓库名称虽为 `second-hand-market-backend`，但本期实际承载完整商家后台工程资产。
3. 若未来团队拆分仓库，当前结构仅作为本期工程组织方案，不影响业务设计。

## 9. 非功能要求总览
1. 鉴权：JWT Access Token + Refresh Token，支持主动失效。
2. 安全：密码哈希（bcrypt/argon2）、接口限流、参数校验、敏感日志脱敏。
3. 可观测性：请求链路 `request_id`、结构化日志、关键指标埋点。
4. 审计：关键操作必须记录操作人、对象、前后状态、结果。
5. 查询体验：统一分页、排序、筛选协议。
6. 可维护性：分层架构、统一错误码、OpenAPI 文档同步。

## 10. 本期交付物
1. 商家后台前端（响应式）可运行版本。
2. 后端 API 服务与数据库迁移脚本。
3. 接口文档、错误码表、审计日志规范。
4. 基础测试（单元/集成/关键流程冒烟）与部署说明。

## 11. 主要风险与应对
1. 风险：订单与商品联动实现不一致。  
   应对：统一状态机校验层 + 事务内同时更新商品与订单 + 唯一约束避免多未完成订单。
2. 风险：移动端页面在表格场景可用性差。  
   应对：列表页提供“表格/卡片”双渲染策略和关键操作底部固定栏。
3. 风险：图片上传链路在不同环境不一致。  
   应对：统一文件服务抽象，开发环境 MinIO 与生产 OSS/S3 走同一接口。
