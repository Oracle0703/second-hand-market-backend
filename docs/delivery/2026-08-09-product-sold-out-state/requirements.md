# 需求说明

| 字段 | 内容 |
|---|---|
| 目标 | 商品移除“已关闭”，保留可补库存恢复的“售罄”，订单继续保留关闭状态 |
| 背景 | 当前商品 `SOLD` 被当作已成交终态，商品另有 `CLOSED`，与最新业务语义冲突 |
| 用户 / 受众 | 商家后台操作员、买家小程序用户、发布运维人员 |
| 提出人 | 用户 |
| 日期 | 2026-08-09 |

## 成功标准

| ID | 标准 | 需要的证据 |
|---|---|---|
| SC-1 | 商品代码、API、商家 UI 和统计不再提供 `CLOSED` | 后端及前端测试、路由检查、构建 |
| SC-2 | 手动售罄和最后一件订单完成后库存为 0、预占为 0、状态为 `SOLD` | Go 回归测试 |
| SC-3 | `SOLD` 只允许补库存，补后转 `OFF_SHELF`，显式上架后恢复销售 | Go 与前端测试 |
| SC-4 | 0 库存或存在活动订单的商品不能上架或快捷售罄 | Go 回归测试 |
| SC-5 | 商家端统一显示“售罄”，提供快捷售罄和售罄补货入口 | Vitest 与构建 |
| SC-6 | 小程序售罄详情可见但详情和收藏页不能发起“我想要” | Vitest 与构建 |
| SC-7 | 历史商品状态通过显式迁移归一化，订单/意向 `CLOSED` 不受影响 | 迁移测试与 SQL 检查 |

## 范围

| 本次范围 | 不在本次范围 |
|---|---|
| 商品状态、库存调整、上架校验、商品统计、商家页面、小程序展示、数据迁移及回归测试 | 新状态码 `SOLD_OUT`、多个活动订单、支付、销售额、商品 `SOLD` 直接删除、恢复隐藏意向页、额外安全与审计治理 |

## 约束

| 类型 | 约束 |
|---|---|
| 技术 | Go/Gin/GORM、React/Vite、Taro；保持现有 API 风格和错误码 |
| 产品 | `SOLD` 展示为“售罄”；补库存不自动上架；商品无 `CLOSED`，订单和意向继续有 `CLOSED` |
| 安全 / 数据 | 不新增安全体系；库存、状态、流水同事务；日志沿用 best-effort |
| 分支 / 发布 | 当前分支 `hotfix/hy/0000_product_sale_status`；迁移先于后端代码发布；不自动提交或推送 |

## 假设

| ID | 假设 | 为什么安全 |
|---|---|---|
| A-1 | 0 库存 `OFF_SHELF` 不直接改为 `SOLD` | 保持销售扣减与盘亏扣减的业务区分 |
| A-2 | 历史 `CLOSED -> OFF_SHELF` 后买家详情可见 | `OFF_SHELF` 已不可购买，且避免新增隐藏字段 |
| A-3 | 快捷售罄使用现有库存调整接口的 `all_remaining=true` | 保留部分 `MARK_SOLD`，同时避免依赖页面缓存库存 |
