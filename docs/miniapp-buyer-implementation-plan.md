# 买家侧小程序实现文档（Taro + React）

## 文档目标
本文基于当前仓库已实现的商家后台能力，反推买家侧小程序可落地实现方案。本文只覆盖本期范围：浏览、搜索、详情、收藏、浏览记录、购买意向提交、游客优先与登录后数据合并，不扩展支付、退款、售后、聊天、推荐算法。

---

# 1. 项目理解

## 1.1 当前后台系统已经实现了什么
当前仓库已实现并闭环了商家后台主链路能力：
1. 商家注册、审核、登录、受限登录（onboarding/full scope）。
2. 商品管理全流程：创建、编辑、上架、下架、关闭、详情、列表。
3. 商家轻量订单：按数量预占、完成或关闭；`LOCKED` 仅保留历史兼容，买家侧不提供下单入口。
4. 分类字典查询、文件上传（presign/confirm）、审计日志。
5. 后端统一错误码、分页规范、状态机约束、集成测试与冒烟脚本。

当前缺口：无买家角色、无买家域接口、无收藏/浏览记录/意向数据模型。

## 1.2 小程序端在整个业务体系中的角色
买家小程序是消费侧入口，承接供给转化：
1. 发现：浏览、分类、搜索。
2. 决策：详情查看、图片预览、收藏、浏览记录。
3. 转化：提交购买意向，形成线索并回流商家后台处理。

## 1.3 买家小程序与商家后台的关系
1. 商家后台负责供给与经营（上架、状态、成交）。
2. 买家小程序负责需求与线索（浏览、收藏、意向）。
3. 两端共享商品主数据与状态语义，但接口域必须隔离，不能把商家接口直接暴露给买家。

## 1.4 本期小程序目标
1. 游客可直接浏览、搜索、查看详情。
2. 游客可收藏、记录浏览历史。
3. 购买意向要求登录后提交。
4. 登录后支持游客数据合并（device_id -> buyer_id）。
5. 买家端可查看简化意向状态（处理中/已联系/已关闭）。

# 2. 默认假设

1. 用户角色
- 游客：默认态，无需登录。
- 注册买家：微信 openid 登录。

2. 游客态能力
- 浏览：允许。
- 收藏：允许。
- 浏览记录：允许。
- 购买意向提交：不允许，必须登录。

3. 登录前后能力边界
- 登录前：浏览、收藏、浏览记录、分享。
- 登录后：增加购买意向提交、我的意向状态查询、跨设备数据同步。

4. 微信登录方式
- 采用游客默认 + 显式授权登录。
- 不采用冷启动强制登录。

5. 手机号绑定策略
- 本期不强制手机号绑定。
- 提交意向时至少填写一种联系方式（手机号或微信号）。

6. 数据同步方式
- 小程序首次启动生成并持久化 `device_id`。
- 游客行为按 `device_id` 归属。
- 登录成功后执行 `device_id -> buyer_id` 合并。

7. 接口复用策略
- 复用底层数据（products/categories/files）与状态语义。
- 不复用商家域业务接口。
- 新增 `/buyer/*` 与配套 `/merchant/intents*`。

8. 分享与预览
- 支持商品分享。
- 支持图片预览。

9. 商品发布与购物车
- 商品发布：不支持。
- 购物车：不支持。

10. 交易能力边界
- 本期做购买意向，不做支付型订单。

# 4. 买家侧核心业务闭环

## 4.1 游客浏览闭环
游客进入 -> 首页浏览 -> 搜索/分类 -> 商品列表 -> 商品详情 -> 收藏/浏览记录。

后端支撑现状：
1. 商品与分类数据可复用。
2. 缺少买家可访问的公开接口，需要新增 `/buyer/products*`、`/buyer/categories`。

## 4.2 游客资产沉淀与登录合并闭环
游客收藏/浏览 -> 显式登录 -> 自动触发 merge -> 数据进入账号态“我的收藏/我的浏览”。

最小规则：
1. 收藏按 `product_id` 去重并集。
2. 浏览记录按 `product_id` 保留最近时间，浏览次数累加。
3. 已合并的游客记录打标，不重复合并。

## 4.3 购买意向最小可行闭环（本期核心）
登录买家提交意向 -> 商家后台查看线索 -> 商家处理 -> 买家查看状态。

### 4.3.1 商家如何查看和处理
商家后台新增“意向线索”模块（必需）：
1. 意向列表页：按状态、时间、关键词（商品标题/联系方式）筛选。
2. 意向详情页：买家联系方式、留言、商品信息、提交时间。
3. 处理动作：
- 标记已联系（`NEW -> CONTACTED`）
- 关闭线索（`NEW/CONTACTED -> CLOSED`，需关闭原因）

### 4.3.2 意向状态流转
内部状态机：
1. `NEW -> CONTACTED`
2. `NEW -> CLOSED`
3. `CONTACTED -> CLOSED`

买家可见简化状态：
1. `NEW` => 处理中
2. `CONTACTED` => 已联系
3. `CLOSED` => 已关闭

### 4.3.3 买家端是否需要看到状态
需要，但仅展示简化状态；不展示商家内部备注和处理人。

### 4.3.4 最小可行闭环定义
1. 买家可提交意向并在“我的意向”看到状态。
2. 商家可在后台处理状态。
3. 状态更新后买家端可读到最新简化状态。

## 4.4 分享转化闭环
分享商品 -> 落地详情 -> 收藏或登录后提交意向。

## 4.5 已下架/已售出处理
1. 列表默认仅展示 `ON_SHELF`。
2. 详情若为 `OFF_SHELF/SOLD/LOCKED`：可查看，不可提交意向。
3. `DRAFT/CLOSED` 对买家不可见。

# 6. 前后端接口复用与缺口分析

## 6.1 总结
1. 可直接复用：products/categories/files 数据与基础状态语义。
2. 可轻改复用：商品查询、分类查询的底层查询逻辑。
3. 必须新增：买家认证、收藏、浏览记录、意向、我的汇总、商家意向处理接口。
4. 不应暴露：`/merchant/products*`、`/merchant/orders*`、`/admin/*`。

## 6.2 分模块拆解

### 6.2.1 商品列表
- 复用现状：`products` 表、分页可复用。
- 差距：现有接口按商家归属查询。
- 建议改法：新增 `GET /api/v1/buyer/products`，默认仅 `ON_SHELF`。

### 6.2.2 商品详情
- 复用现状：商品与图片关联可复用。
- 差距：现有详情仅商家可访问且返回 `file_id`。
- 建议改法：新增 `GET /api/v1/buyer/products/:id`，返回图片 URL 和可提交标记。

### 6.2.3 分类
- 复用现状：`categories` 可复用。
- 差距：现有分类接口需要商家 full scope。
- 建议改法：新增 `GET /api/v1/buyer/categories`。

### 6.2.4 登录/认证
- 复用现状：JWT/session 框架可复用。
- 差距：现有仅 ADMIN/MERCHANT。
- 建议改法：新增 BUYER 用户类型和 `/api/v1/buyer/auth/*`。

### 6.2.5 收藏
- 复用现状：无。
- 差距：无表无接口。
- 建议改法：新增 `buyer_favorites` + `GET/POST/DELETE /api/v1/buyer/favorites`。

### 6.2.6 浏览记录
- 复用现状：无。
- 差距：无表无接口。
- 建议改法：新增 `buyer_histories` + `POST views`、`GET`、`DELETE`。

### 6.2.7 购买意向
- 复用现状：商家订单字段有联系方式，但语义不匹配。
- 差距：商家订单属于商家经营域，权限和成交语义都不适合作为买家线索入口。
- 建议改法：新增 `buyer_intents`，独立于商家订单状态机；并新增商家处理接口。

### 6.2.8 我的页面
- 复用现状：无买家聚合接口。
- 差距：无账号态统计数据。
- 建议改法：新增 `GET /api/v1/buyer/me/summary`。

## 6.3 风控与频控建议（接口级）
1. 收藏写入：60 req/min/owner。
2. 浏览上报：120 req/min/owner；同商品 30 秒内去重。
3. 微信登录：20 req/min/device，120 req/min/IP。
4. 意向提交：5 req/min/buyer，20 req/day/buyer，30 req/day/device。
5. 意向重复提交：同买家同商品仅允许 1 条未关闭意向。

# 7. 数据与状态设计

## 7.1 token 与 refresh token
1. 登录后保存 `access_token`、`refresh_token`。
2. 401 自动 refresh，失败则回游客态。

## 7.2 device_id
1. 首次启动生成 UUID 并持久化。
2. 全量请求携带 `X-Device-Id`。

## 7.3 游客态数据
1. 收藏、浏览记录允许游客态写入。
2. 意向提交必须登录。

## 7.4 登录后合并策略（device_id -> buyer_id）
1. 合并触发：微信登录成功后自动触发一次。
2. 收藏合并：按 `product_id` 去重并集。
3. 浏览合并：按 `product_id` 合并，`last_viewed_at` 取最新，`view_count` 累加。
4. 合并打标：记录 `merge_target_buyer_id`、`merged_at`，避免重复合并。

## 7.5 一台设备多账号 / 一个账号多设备
1. 一台设备多账号：
- 每次仅合并“未合并的游客数据”。
- 已归并到账号 A 的数据不会自动迁移到账号 B。
2. 一个账号多设备：
- 允许多设备登录同一账号。
- 多设备合并时按唯一约束去重。

## 7.6 小程序缓存策略
1. 商品列表按查询条件缓存。
2. 搜索历史本地存储最近 10 条。
3. 收藏状态乐观更新失败回滚。

# 9. 风险与边界

1. 当前后端是商家后台，不天然适合买家端。
2. 硬复用商家订单接口会绕过买家线索边界，并直接产生库存预占和成交记录。
3. 意向闭环若不新增商家线索处理模块，会形成“买家提交后无人处理”的断链。
4. 二期延后项：支付、退款、售后、聊天、推荐。

# 11. 最终结论

1. 当前后端系统是否已经足以支撑买家小程序第一版？
- 还不足以直接支撑，需要新增买家域与商家意向处理能力。

2. 买家小程序第一版最小可行范围（MVP）
- 游客浏览、收藏、浏览记录。
- 显式登录后提交购买意向。
- 买家可查看简化意向状态。

3. 需要补的后端能力
1. `/api/v1/buyer/*` 认证与业务接口。
2. 买家数据模型与合并机制。
3. 商家后台意向线索处理模块与接口。

4. 现在优先做哪 3 个页面
1. 商品详情页
2. 登录页（含意向提交回跳）
3. 意向提交页

5. 当前小程序文档是否已达到可进入任务拆解阶段
- 是。当前三份文档已形成实现文档 + 数据模型 + 接口 checklist 的决策闭环，可直接进入任务拆解。
