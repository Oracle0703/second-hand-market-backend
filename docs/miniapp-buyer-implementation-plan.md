# 买家侧小程序实现文档（Taro + React）

## 文档目标
本文基于当前仓库已实现的商家后台能力，反推买家侧小程序可落地实现方案。本文只覆盖本期范围：浏览、搜索、详情、收藏、浏览记录、购买意向提交、游客优先与登录后数据合并。

---

# 1. 项目理解

## 1.1 当前后台系统已经实现了什么
当前仓库已实现并闭环了商家后台主链路能力：
1. 商家注册、审核、登录、受限登录（onboarding/full scope）。
2. 商品管理全流程：创建、编辑、上架、下架、关闭、详情、列表。
3. 轻量订单：创建、完成、关闭，并与商品状态事务联动（LOCKED/SOLD/OFF_SHELF）。
4. 分类字典查询、文件上传（presign/confirm）、审计日志。
5. 后端统一错误码、分页规范、状态机约束、集成测试与冒烟脚本。

注意：当前系统没有买家角色、没有买家域接口、没有收藏/浏览记录/意向数据模型。

## 1.2 小程序端在业务体系中的角色
买家小程序是消费侧入口，目标是将商家后台已上架商品转化为买家行为：
1. 发现：浏览、分类、搜索。
2. 决策：详情查看、图片预览、收藏、浏览记录沉淀。
3. 转化：提交购买意向，沉淀线索给商家后续跟进。

## 1.3 买家小程序与商家后台的关系
1. 商家后台负责供给（商品上架、状态维护、订单结单）。
2. 买家小程序负责需求（浏览、收藏、意向）。
3. 两端共享商品主数据与状态语义，但接口必须按域隔离，不能把商家接口直接给买家使用。

## 1.4 本期小程序目标
在不扩展支付、退款、售后、IM、推荐算法的前提下，完成最小可行买家闭环：
1. 游客可浏览、搜索、查看详情。
2. 游客可收藏、积累浏览记录、提交购买意向。
3. 登录后可将游客数据恢复/合并到账号。
4. 商品分享后可落地详情并促进收藏/意向转化。

# 2. 默认假设

以下假设用于填补当前仓库没有显式定义的买家侧信息缺口：

1. 用户角色
- 游客用户：默认态，无需登录。
- 注册买家：通过微信 openid 登录（本期默认方案）。

2. 游客态是否允许浏览
- 允许。首页、分类、搜索、列表、详情均可访问。

3. 游客态是否允许收藏/浏览记录/意向提交
- 允许。以 `device_id` 作为游客唯一标识进行本地+服务端关联。

4. 登录前后能力边界
- 登录前：可完成浏览、收藏、浏览记录、意向提交。
- 登录后：新增跨设备同步、历史资产归并、账号化“我的”视图。
- 本期无必须登录才能提交意向的强制规则。

5. 数据同步方式
- 小程序启动生成并持久化 `device_id`。
- 游客行为先按 `device_id` 落地。
- 登录后调用合并接口，将 `device_id` 数据归并到 `buyer_id`。

6. 小程序端与后台接口复用策略
- 复用底层数据与状态语义（products/categories/files/stateflow）。
- 不直接复用 `/merchant/*` 与 `/admin/*` 业务接口。
- 新增 `/buyer/*` 接口域承接买家能力。

7. 是否支持分享
- 支持。分享商品详情页，携带 `product_id` 落地参数。

8. 是否支持图片预览
- 支持。详情页支持多图预览。

9. 是否支持商品发布
- 不支持（本期明确禁止买家端发布能力）。

10. 是否支持购物车
- 不支持（本期不做购物车和支付交易链路）。

11. 是否支持订单/预约/购买意向
- 支持“购买意向”能力，不支持支付型订单。
- 买家端不复用商家订单创建接口，避免触发商品锁定。

# 3. 本期范围 / 非范围

## 3.1 本期一定做什么
1. 商品消费链路：首页浏览、分类、搜索、商品列表、商品详情。
2. 游客优先链路：游客收藏、浏览记录、意向提交。
3. 登录链路：微信 openid 登录、游客数据恢复/合并。
4. 我的链路：我的收藏、我的浏览记录、我的意向汇总。
5. 分享链路：分享商品 -> 打开详情 -> 转化操作。
6. 商品不可售状态展示：已下架/已售出提示与动作限制。

## 3.2 本期明确不做什么
1. 支付、退款、售后、发票。
2. 即时聊天（IM）、推荐算法、营销活动。
3. 商家商品管理（新增/编辑/上下架）。
4. 购物车与履约订单系统。

## 3.3 哪些能力继续沿用后台系统
1. 商品、分类、文件元数据结构。
2. 商品状态定义与状态机语义。
3. 通用响应结构、错误码规范、鉴权中间件框架。

## 3.4 哪些能力需要为买家端单独设计
1. 买家认证体系（openid -> buyer session）。
2. 买家行为模型（收藏、浏览记录、意向）。
3. 游客 `device_id` 识别、登录后合并策略。
4. 买家端聚合接口（我的页面）。

# 4. 买家侧核心业务闭环

## 4.1 游客进入 -> 浏览首页 -> 搜索/筛选 -> 商品详情
1. 首次进入生成 `device_id` 并持久化。
2. 首页展示可售商品入口（默认 `ON_SHELF`）。
3. 进入搜索页或分类页，筛选后进入商品列表。
4. 点击商品进入详情，查看图文与状态。

当前后端卡点：
1. 没有买家可用商品列表/详情接口。
2. 没有公共分类接口（现有分类接口受商家 full scope 限制）。

## 4.2 游客 -> 收藏/浏览记录 -> 登录 -> 数据恢复/合并
1. 游客收藏商品、形成浏览记录。
2. 登录后发起 `guest merge`，按 `device_id` -> `buyer_id` 合并。
3. 合并完成后在“我的收藏/我的浏览”中可见历史数据。

当前后端卡点：
1. 缺少收藏、浏览记录数据模型与接口。
2. 缺少登录后游客数据合并接口。

## 4.3 登录用户 -> 收藏商品 -> 提交购买意向
1. 登录买家在详情页点击收藏。
2. 点击“提交购买意向”，填写联系方式与备注。
3. 意向单创建成功，进入“我的意向”查看状态。

当前后端卡点：
1. 缺少买家意向接口。
2. 现有商家订单接口不适合作为买家意向接口（会锁定商品状态）。

## 4.4 分享商品 -> 落地详情 -> 转化为收藏/意向
1. 买家分享商品详情卡片。
2. 被分享者打开小程序后落地到商品详情页。
3. 若商品在售可继续收藏/提意向；若不可售展示状态说明。

当前后端卡点：
1. 缺少买家详情接口与分享参数解析后的数据接口契约。

## 4.5 已下架 / 已售出商品展示规则
1. 列表默认只展示 `ON_SHELF`（可售）。
2. 已分享直链进入详情时，如状态是 `OFF_SHELF/SOLD/LOCKED`：
- 允许查看详情
- 禁用“提交意向”按钮
- 显示对应状态文案
3. `DRAFT/CLOSED` 不对买家端暴露。

当前后端卡点：
1. 缺少买家视角的状态映射和过滤接口。

# 6. 前后端接口复用与缺口分析

## 6.1 结论总览
1. 可直接复用：数据表与状态语义（products/categories/files）。
2. 可轻改复用：分类查询与商品查询的底层查询逻辑。
3. 必须新增：买家认证、收藏、浏览记录、购买意向、游客合并、我的聚合接口。
4. 不能暴露：商家与管理员业务接口。

## 6.2 分模块分析（复用现状 / 差距 / 建议改法）

### A. 商品列表
1. 复用现状
- `products` 表、商品状态字段、分页规范可复用。
2. 差距
- 现有 `GET /merchant/products` 按 `merchant_id` 查自己的商品，不是买家视角。
- 返回字段偏后台管理视角，缺少买家展示字段（图片 URL、商家信息、收藏态）。
3. 建议改法
- 新增 `GET /api/v1/buyer/products`。
- 默认过滤 `status=ON_SHELF`，支持 `keyword/category_id/page/page_size/sort`。
- 返回买家展示 DTO，包含 `is_favorited`（按 buyer/device 计算）。

### B. 商品详情
1. 复用现状
- 可复用 `products + product_images + files` 关联关系。
2. 差距
- 现有 `GET /merchant/products/:id` 仅商家可访问。
- 当前详情返回图片 `file_id` 列表，不适合小程序直接展示。
3. 建议改法
- 新增 `GET /api/v1/buyer/products/:id`。
- 返回图片 URL 列表、可操作标记（`can_submit_intent`）、状态说明。
- 支持不可售商品详情只读展示。

### C. 分类
1. 复用现状
- `categories` 表和现有查询逻辑可复用。
2. 差距
- 现有 `GET /merchant/categories` 仅 `MERCHANT(full)` 可访问。
3. 建议改法
- 新增 `GET /api/v1/buyer/categories`（PUBLIC/BUYER 均可访问）。
- 仅返回 `ENABLED` 分类，结构适配小程序级联。

### D. 登录/注册
1. 复用现状
- JWT、refresh session、logout 框架可复用。
2. 差距
- 现有登录只支持 `ADMIN/MERCHANT`。
- 无买家账号体系，无微信 code 换会话流程。
3. 建议改法
- 新增 `buyer_users` 表。
- 新增 `POST /api/v1/buyer/auth/wechat-login`（`code + device_id`）。
- 扩展 refresh/logout 到买家用户类型。

### E. 收藏
1. 复用现状
- 无。
2. 差距
- 没有收藏表/接口。
3. 建议改法
- 新增 `buyer_favorites` 表。
- 新增：
  - `GET /api/v1/buyer/favorites`
  - `POST /api/v1/buyer/favorites`
  - `DELETE /api/v1/buyer/favorites/:product_id`
- 支持 `buyer_id` 或 `device_id` 归属。

### F. 浏览记录
1. 复用现状
- 无。
2. 差距
- 没有浏览记录表/接口。
3. 建议改法
- 新增 `buyer_histories` 表。
- 新增：
  - `POST /api/v1/buyer/history/views`
  - `GET /api/v1/buyer/history`
  - `DELETE /api/v1/buyer/history`
- 同商品重复浏览更新最近时间。

### G. 意向提交 / 联系商家 / 轻量下单
1. 复用现状
- 现有商家订单有联系方式字段，但业务语义是商家经营动作。
2. 差距
- 买家调用商家订单接口会触发商品锁定，和买家意向语义冲突。
3. 建议改法（本期选型：购买意向）
- 新增 `buyer_intents` 表。
- 新增：
  - `POST /api/v1/buyer/intents`
  - `GET /api/v1/buyer/intents`
- 意向提交不改变商品状态，不进入商家订单状态机。

### H. 我的页面
1. 复用现状
- 现有 `merchant/account` 仅商家可用，不可复用给买家。
2. 差距
- 缺少买家资料、收藏数/浏览数/意向数聚合接口。
3. 建议改法
- 新增 `GET /api/v1/buyer/me/summary`，支持游客态与登录态返回不同结构。

## 6.3 不应暴露给买家端的接口
1. `/api/v1/merchant/products*`
2. `/api/v1/merchant/orders*`
3. `/api/v1/merchant/account*`
4. `/api/v1/merchant/dashboard`
5. `/api/v1/merchant/logs`
6. `/api/v1/admin/*`

# 7. 数据与状态设计

## 7.1 客户端状态与存储
1. `token`
- 登录后保存 `access_token`。
- 请求自动注入，401 时尝试 refresh。

2. `refresh token`
- 登录态持久化保存。
- 退出时清理本地并调用后端注销。

3. `device_id`
- 首次启动生成 UUID 并持久化。
- 全部请求携带 `X-Device-Id`。

4. 游客态数据
- 收藏、浏览记录、意向草稿本地落盘。
- 联网时按 `device_id` 同步服务端。

5. 登录后合并策略
- 调用 `POST /api/v1/buyer/guest/merge`。
- 收藏：按 `product_id` 去重并集。
- 浏览记录：按 `product_id` 保留最近 `viewed_at`。
- 意向：按 `device_id` 绑定至当前 `buyer_id`，避免重复提交。

6. 商品列表缓存
- 按筛选条件构建缓存 key。
- 切后台返回后优先读缓存再增量刷新。

7. 搜索历史
- 本地保存最近 10 条关键词。
- 本期默认本地，不强制服务端同步。

8. 收藏状态
- 列表与详情共享同一状态源。
- 支持乐观更新，失败回滚。

9. 浏览记录
- 进入详情页即上报（节流防抖）。
- 支持清空记录。

10. 分享落地参数
- 解析 `product_id`。
- 若商品不可售，展示只读状态页与提示文案。

# 8. 技术方案

## 8.1 技术栈
1. 前端：`Taro + React + TypeScript`。
2. 目标平台：微信小程序。

## 8.2 状态管理方案
1. 远程状态：TanStack Query（列表缓存、详情缓存、失效管理）。
2. 本地会话状态：Zustand（auth/device/guest flags）。

## 8.3 请求层方案
1. 基于 `Taro.request` 封装统一 `http`。
2. 请求拦截：
- 注入 `Authorization`（登录态）
- 注入 `X-Device-Id`（全量）
3. 响应拦截：
- 统一错误码处理
- 401 自动刷新或回退游客态

## 8.4 页面组织结构建议
1. `pages`：页面容器与路由入口。
2. `components`：可复用展示组件。
3. `hooks`：页面逻辑组合（列表、详情、收藏、合并）。
4. `services`：接口请求与 DTO。
5. `stores`：全局状态。
6. `utils`：存储、分享、格式化、设备能力。

# 9. 风险与边界

1. 当前后端主要是商家后台，不天然适合买家端。
- 若直接复用商家接口，会出现权限模型错位与数据暴露风险。

2. 硬复用商家订单接口会导致体验差。
- 商家订单创建会锁定商品状态，不符合“买家意向”语义。

3. 必须新增后端接口的能力
- 买家认证（openid）
- 买家公共商品接口
- 收藏、浏览记录、购买意向
- 游客合并接口
- 我的聚合接口

4. 应延后二期能力
- 支付、退款、售后
- IM 聊天
- 推荐算法与营销系统
- 购物车与履约订单系统

# 10. 实施顺序

## 第 1 阶段：只读链路 MVP（可浏览）
1. 后端新增：`/buyer/categories`、`/buyer/products`、`/buyer/products/:id`。
2. 小程序完成：首页、分类、搜索、列表、详情、分享落地。
3. 阶段产出：游客无需登录可完整浏览商品。

## 第 2 阶段：游客行为与登录合并（可沉淀）
1. 后端新增：买家登录、收藏、浏览记录、游客合并。
2. 小程序完成：收藏页、浏览记录页、登录页、游客引导页。
3. 阶段产出：游客可沉淀行为，登录后可恢复/合并。

## 第 3 阶段：意向闭环与我的页（可转化）
1. 后端新增：购买意向接口、我的汇总接口。
2. 小程序完成：意向提交页、我的页聚合展示。
3. 阶段产出：浏览 -> 收藏/记录 -> 意向提交闭环跑通。

# 11. 最终结论

1. 当前后端系统是否已经足以支撑买家小程序第一版？
- 不能直接支撑完整闭环。
- 可复用商品/分类/状态机等底层能力，但买家域核心能力缺失。

2. 买家小程序第一版的最小可行范围是什么？
- 游客浏览（首页/搜索/列表/详情）
- 收藏与浏览记录
- 购买意向提交
- 登录后游客数据合并
- 我的页基础汇总

3. 需要补哪些后端能力才能闭环？
1. 买家认证（微信 openid）。
2. 买家公共商品与分类接口。
3. 收藏、浏览记录、意向接口与数据表。
4. 游客 `device_id` 合并接口。
5. 我的页面聚合接口。

4. 如果现在立刻开始开发，小程序最适合先做哪 3 个页面？
1. 首页（流量入口）
2. 商品列表页（搜索/分类承接页）
3. 商品详情页（收藏/意向/分享转化页）
